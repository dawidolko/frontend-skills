## 1. WCAG 2.2 facts a rule writer needs

- Status: W3C Recommendation; the live /TR/WCAG22/ page is the 12 December 2024 version (https://www.w3.org/TR/WCAG22/).
- Count read from the spec markup today: **31 Level A + 24 Level AA = 55 criteria** to cover for AA (plus 31 AAA). (Counted from every `Success Criterion x.y.z` section and its "(Level …)" line.)
- **4.1.1 Parsing is "Obsolete and removed"** in 2.2: the spec note says AT no longer parses HTML directly, so the problems it addressed are gone or covered elsewhere (https://www.w3.org/TR/WCAG22/#parsing). Consequence: do not report duplicate ids / unclosed tags as a WCAG failure; only report duplicate ids when they break a reference (`for`, `aria-labelledby`, `aria-describedby`), which is a 1.3.1 / 4.1.2 problem. axe-core already moved `duplicate-id` and `duplicate-id-active` to "Deprecated" and keeps `duplicate-id-aria` under 4.1.2.
- **New in 2.2** (spec section "New Features in WCAG 2.2", https://www.w3.org/TR/WCAG22/#new-features-in-wcag-2-2), 9 criteria:

| SC | name | level |
|---|---|---|
| 2.4.11 | Focus Not Obscured (Minimum) | AA |
| 2.4.12 | Focus Not Obscured (Enhanced) | AAA |
| 2.4.13 | Focus Appearance | AAA |
| 2.5.7 | Dragging Movements | AA |
| 2.5.8 | Target Size (Minimum) | AA |
| 3.2.6 | Consistent Help | A |
| 3.3.7 | Redundant Entry | A |
| 3.3.8 | Accessible Authentication (Minimum) | AA |
| 3.3.9 | Accessible Authentication (Enhanced) | AAA |

  So 6 of the 9 are in scope for A/AA. New criteria were appended at the end of each guideline, so numbering is no longer grouped by level (same section).
- The spec says pages that conform to 2.2 also conform to 2.1, and the WG recommends 2.2 as the target even where rules cite older versions (same section).
- **Large-scale text** (glossary, https://www.w3.org/TR/WCAG22/#dfn-large-scale): at least 18 pt, or 14 pt bold (or equivalent for CJK fonts). Understanding 1.4.3 converts with 1pt = 1.333px: **18pt ≈ 24 CSS px, 14pt ≈ 18.5 CSS px** (https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). Size means the delivered size, not after user zoom. In code: large if `font-size ≥ 24px`, or `font-size ≥ 18.5px` and `font-weight ≥ 700`.
- **Contrast ratio** = (L1 + 0.05) / (L2 + 0.05) with relative luminance of lighter (L1) and darker (L2) colour; range 1:1 to 21:1 (https://www.w3.org/TR/WCAG22/#dfn-contrast-ratio). Thresholds: 1.4.3 text 4.5:1, large text 3:1; 1.4.11 UI components / graphics 3:1 against adjacent colours. Compare unrounded values: Understanding 1.4.3 treats the ratios as hard thresholds (its example: 4.499:1 does not meet 4.5:1).
- **Target size 2.5.8**: 24×24 CSS px, or the 24 px-circle spacing test; exceptions Spacing, Equivalent, Inline, User-agent control, Essential (https://www.w3.org/TR/WCAG22/#target-size-minimum).
- **Reflow 1.4.10**: 320 CSS px wide for vertical-scrolling content (= 1280 px at 400 %), 256 CSS px high for horizontal-scrolling content (https://www.w3.org/TR/WCAG22/#reflow).
- **Text spacing 1.4.12** override values: line-height 1.5×, paragraph spacing 2×, letter spacing 0.12×, word spacing 0.16× font size (https://www.w3.org/TR/WCAG22/#text-spacing).
- **Input purposes (1.3.5)**: WCAG §7 lists 53 tokens, based on the HTML autofill field names (https://www.w3.org/TR/WCAG22/#input-purposes), e.g. `name`, `given-name`, `family-name`, `email`, `tel`, `street-address`, `postal-code`, `country-name`, `bday`, `cc-number`, `cc-exp`, `username`, `new-password`, `current-password`, `organization`, `language`, `url`. Note: `one-time-code` is an HTML autofill token but not in the WCAG §7 list (useful for 3.3.8, not required by 1.3.5).
- **Cognitive function test (3.3.8)**: remembering, manipulating or transcribing information (memorising passwords, typing characters, spelling, calculating, puzzles); entering one's own name, email or phone is explicitly not one (https://www.w3.org/TR/WCAG22/#dfn-cognitive-function-test). The SC notes name password-manager support and copy-paste as acceptable helper mechanisms.
- **C39 (prefers-reduced-motion)** is listed as sufficient only for 2.3.3 Animation from Interactions, which is **AAA** (https://www.w3.org/WAI/WCAG22/Techniques/css/C39). It is not a sufficient technique for any A/AA criterion; it is still a cheap default and partly helps 2.2.2.
- Techniques are informative: the Techniques pages state that content can meet WCAG without using them. Failures (F-ids) are the most useful source for automated rules because each describes a pattern that does not meet the criterion.

### 4.3 W3C ACT Rules – shared ground

- ACT rules (https://www.w3.org/WAI/standards-guidelines/act/rules/) are W3C-published, informative test rules for WCAG 2.2 and ARIA; tools publish implementation reports against them, so an ACT rule id is the most tool-neutral reference for an automated check. The page filters by WCAG 2.2 A/AA/AAA, by status (approved / proposed / deprecated) and by implementation type (manual, semi-automatic, automated, linter).
- Counting the `data-status` attributes in today's page markup gave 84 distinct rule links: 37 approved, 44 proposed, 3 deprecated (my count; may differ from W3C's own totals).
- axe-core tags rules that implement ACT rules with `ACT` and lists `actIds` in rule metadata (e.g. `meta-viewport` → `b4f0c3`, seen in `lib/rules/meta-viewport.json` v4.14.0). IBM's engine README points to its ACT implementation report.
- Rule writers: where an ACT rule exists, put its id next to the axe id in the `source` of our rule; it makes results comparable across axe / IBM / others.

### 4.4 What only a person can check (summary)

Quality and equivalence of alt text, captions, transcripts, link and heading wording; reading and focus order versus visual order; keyboard traps and full keyboard operation of custom widgets; focus visibility and focus obscured by sticky UI; screen-reader announcements of state changes and status messages; hover/focus popups behaviour; reflow and 200 % zoom on real layouts; non-text contrast of borders/icons/charts; colour-only meaning; drag and gesture alternatives; consistent navigation/help across pages; error messages and suggestions; authentication steps; timing and motion. Automated results should be reported as "found N problems; M items need a person", never as "accessible".

## 5. Context: European Accessibility Act and EN 301 549 (no legal advice)

- **Directive (EU) 2019/882** (EAA), OJ L 151 of 7.6.2019 (https://publications.europa.eu/resource/celex/32019L0882): Art. 31 – Member States adopt measures by **28 June 2022** and **apply them from 28 June 2025**. Art. 2(2) covers services to consumers after 28 June 2025, including **e-commerce services**, consumer banking, e-books, electronic communications, and websites/apps of passenger transport services. Art. 4(5) exempts **microenterprises providing services**. Art. 32 has transitional periods (products already used to provide services until 28 June 2030; self-service terminals up to 20 years).
- **EN 301 549**, the harmonised European standard for ICT accessibility:
  - **V3.2.1 (2021-03)**: clause 9 (Web) states that conforming to **WCAG 2.1 Level AA** is equivalent to meeting clauses 9.1–9.4 plus 9.6 (https://www.etsi.org/deliver/etsi_en/301500_301599/301549/03.02.01_60/en_301549v030201p.pdf, clause 9.0). It was prepared for Directive (EU) 2016/2102 (public-sector websites).
  - **V4.1.1 (2026-09)** is published on the ETSI server: clauses 9–11 are updated to align with **WCAG 2.2**; clause 9.0 maps WCAG 2.2 AA to all of 9.1–9.4 + 9.6 (and WCAG 2.1 AA to the same minus 9.2.4.11, 9.2.5.7, 9.2.5.8, 9.3.2.6, 9.3.3.7, 9.3.3.8). Its foreword says it was prepared under standardisation request C(2022) 6456 to support Directive (EU) 2019/882 (Annex ZB) and that presumption of conformity applies **once it is cited in the Official Journal**. Dates in the document: adoption 24 August 2026, doa 30 November 2026, dop/e 31 May 2027, dow 31 May 2028 (https://www.etsi.org/deliver/etsi_en/301500_301599/301549/04.01.01_60/en_301549v040101p.pdf).
  - axe-core already has an `EN-301-549v4` tag next to `EN-301-549`.
  - Practical reading for our wording: WCAG 2.2 AA is a superset of 2.1 AA, so working to 2.2 AA covers what V3.2.1 references; whether V4.1.1 is cited in the OJ was not verified.
- **Poland** (official Sejm ELI API):
  - Ustawa z dnia 26 kwietnia 2024 r. o zapewnianiu spełniania wymagań dostępności niektórych produktów i usług przez podmioty gospodarcze, **Dz.U. 2024 poz. 731**, implements Directive 2019/882; in force from **28 June 2025** (except a few articles); Art. 4 pkt 1 excludes services offered by microenterprises (https://api.sejm.gov.pl/eli/acts/DU/2024/731/text.html).
  - Ustawa z dnia 4 kwietnia 2019 r. o dostępności cyfrowej stron internetowych i aplikacji mobilnych podmiotów publicznych, **Dz.U. 2019 poz. 848**, implements Directive 2016/2102 for public bodies; requirements are in its annex (https://api.sejm.gov.pl/eli/acts/DU/2019/848/text.html). Which WCAG version that annex mirrors was not checked.
- Our tool must not say a site "complies with the EAA" or "meets EN 301 549"; it can say which findings map to which WCAG criterion (and, via axe tags, to EN 301 549 clause numbers `EN-9.x.x.x`).

## 6. Notes for skill authors

- **Short skill (always loaded):** the 10–15 error-level rules that are cheap to apply while writing code: `img-alt`, `icon-button-name`, `input-label`, `interactive-is-native`, `link-is-link`, `focus-visible`, `text-contrast`, `ui-contrast`, `target-size`, `html-lang`, `page-title`, `viewport-zoom`, `status-message-live`, `auth-allow-paste`, `no-positive-tabindex`; plus the "large text = 24px / 18.5px bold" and "24×24 target" numbers and the rule "prefer native HTML over ARIA". Keep the honesty sentence about automated limits.
- **Reference file:** the full SC table of §2 (with technique links), the rest of §3, the axe/Lighthouse mapping of §4, EAA/EN context of §5.
- **Noisy / controversial:** `heading-order` and `one-h1` are best practice, not WCAG failures (keep as info). `color-with-background` (F24) is noisy in component CSS. Static contrast checks give false positives with CSS variables, opacity, `mix-blend-mode`, gradients – prefer runtime axe. `reduced-motion` is AAA-sourced (C39) – recommend, don't fail. `no-autofocus` depends on context. Static "drag without alternative", "sticky header without scroll-padding" and "toast without live region" are heuristics – report as warnings that ask for a manual check. Lighthouse 100 ≠ accessible; don't optimise for the score.
- **Changes often, recheck before release:** axe-core version, rule count, which rules are on by default (watch `target-size` and the `wcag22aa` set), Lighthouse weights (they follow axe impacts and are edited by hand), Deque's coverage figure, ACT rule statuses, EN 301 549 V4.1.1 OJ citation, technique ids on Understanding pages (W3C adds/retires techniques; e.g. ARIA21 `aria-invalid` exists in the index but is not linked from any A/AA Understanding page today).
- **Don't duplicate:** component patterns (APG), focus management inside dialogs/menus/tabs and component-library advice live in the other agent's file; link to it from `a11y/dynamic-content-after-trigger`, `a11y/no-keyboard-trap` and `a11y/state-exposed`.
- **Licences of tools we might call:** axe-core and its wrappers MPL-2.0 (use as dependency, don't copy source), pa11y LGPL-3.0-only, Lighthouse and IBM checker Apache-2.0, jsx-a11y MIT, WAVE proprietary with an automated-use ban.
