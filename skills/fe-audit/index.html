Workflow

Audit the project

Audits a front-end project with frontend-skills - runs the static audit (and the page audit with --url when a page is running), reads the condensed JSON, explains the top findings by rule id with their source, lists what needs a person, and proposes an order of fixes. Use when asked to audit, check or score a project or page, "what is wrong with this site", or before a release.

fe-auditevery web project5 rules83 tokens always loaded, 778 tokens when used, 731 tokens in references on demand.

Install

init installs this skill when the project uses every web project. Pick your agent to see where its files land.

Run with
Agent
npx github:dawidolko/frontend-skills init

How to use it

Once installed, the agent loads the skill by itself when a task matches its description. You can also ask for it in your own words, for example:

Phrases from the skill description that make the agent pick it:

  • what is wrong with this site

And to check and fix the work:

  • Use the fe-audit skill on this file.
  • Run the front-end audit on what I changed and fix everything serious.
  • Explain a11y/control-name and fix it here.

Rules it teaches

  • a11y/control-name

    Every button and link has an accessible name; icon-only controls get visually hidden text or aria-label.

    criticalstaticWCAG 4.1.2, 2.4.4

  • a11y/input-label

    Every form field has a programmatic label (label element, aria-label or aria-labelledby); a placeholder is not a label.

    criticalstaticWCAG 1.3.1, 3.3.2, 4.1.2

  • a11y/img-alt

    Every img and area element has an alt attribute; a decorative image has alt="".

    criticalstaticWCAG 1.1.1

  • a11y/color-contrast

    Text has a contrast ratio of at least 4.5:1 with its background; large text (24px, or 18.5px bold) at least 3:1.

    seriousbrowserWCAG 1.4.3

  • perf/lcp-image

    The LCP image is in the initial HTML, not lazy, and has fetchpriority="high"; a CSS background LCP image is preloaded.

    moderatebrowser

The rule digest

This part is copied into each agent's scoped rule file, so it stands on its own:

  • Run the audit, do not imitate it: npx github:dawidolko/frontend-skills audit --json and read the JSON, not the source by eye.
  • Run the page audit only on a page the person started, with their yes: audit --url <address>.
  • Present findings by rule id, severity first: critical, serious, moderate, minor.
  • For each top rule say why it matters, the fix and how many places; explain <id> gives the text and the source.
  • Blocking problems first: missing names and labels (a11y/control-name, a11y/input-label, a11y/img-alt) before contrast (a11y/color-contrast) and speed (perf/lcp-image).
  • Group fixes by file and by shared component, so one change clears many findings.
  • List what the audit cannot check (browser rules without --url, manual rules) as a checklist for a person.
  • Never claim the project is accessible, compliant, secure or fast; say "N problems found, M items need a person".
  • Never change files during an audit; propose the fixes and let fe-fix apply them.

Steps the agent follows

  1. npx github:dawidolko/frontend-skills audit --json (add --changed for only the changed files). Exit code 1 means something is at or above failOn; 2 is a usage error; 3 means a requested tool is missing.
  2. Read counts, then each entry of rules: severity s, fix, locations at (file:line).
  3. If a dev or preview server is running and the person agrees: audit --url http://localhost:5173/ --json for contrast, rendered names, Lighthouse scores and lab metrics.
  4. Write a short summary: counts by severity, the five rules that matter most with their fix and count, the shared components to fix first, the manual checklist.
  5. Point to frontend-report.md for the full list with sources, and to explain <id> for any rule.

How the agent checks the work

  • The summary names rule ids that exist (frontend-skills list --rules), and every location is file:line from the JSON.
  • The person can rerun the same command and get the same counts.
