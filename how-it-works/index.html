How it works

Two things in one repository: a dictionary (skills that tell an agent how to write front-end code, and rules with stable ids) and a command that fits the dictionary to one project.

The project profile

init and learn read the project in one pass with no network: package.json files (and workspaces in a monorepo), lockfiles, config files such as next.config.*, angular.json or tailwind.config.*, and installed versions from node_modules. A folder without package.json that holds HTML, CSS and JavaScript counts as a plain site. The result is .frontend-skills/profile.json, committed with the project:

stack decides which skills are installed: a skill is installed when the profile has any of the keys it requires. The audit object is yours; learn and update keep it.

Your project's own helpers

Rules follow the project's conventions when it has them. The profile records helpers such as a px-to-rem function, generated icon classes, an SVG sprite, design tokens or a set of custom properties, and the rules that depend on them name your helper: "write sizes with rem-calc(16px)" instead of a generic hint. You can correct or add a helper in the profile; your entries survive learn and update.

Files for each agent

A skill is written once as an Agent Skills folder (SKILL.md, references/, scripts/). Each agent has an adapter that knows where that agent looks and in which format. Nobody edits the generated files; update rewrites them and uninstall removes them.

One folder for most agents

Many agents read the shared .agents/skills/ folder, and some read two folders and would list each skill twice. The installer picks the smallest set of folders that every chosen agent reads, with the fewest duplicates, and names any duplicate it could not avoid; doctor checks it again later.

Your instruction files stay yours

Shared files such as AGENTS.md, CLAUDE.md or GEMINI.md get one short block between <!-- frontend-skills:start --> and <!-- frontend-skills:end -->. Text outside the block is never touched, a second run replaces the block in place, and a file is created only when it did not exist.

Rules scoped to file types

Where an agent supports it, each skill also gets a short rule file with the skill's rule digest and the file patterns it is about, so a CSS rule is not loaded while the agent edits a test. Lessons

When you confirm something about your project ("form fields use our Field component"), it is kept as one line in .frontend-skills/lessons.md, and every skill reads that file first. A lesson is at most 300 characters, may name the rule ids it concerns, and is refused when it looks like a secret.

Record a lesson:

npx github:dawidolko/frontend-skills learn --lesson "Form fields use components/ui/Field.tsx" --kind convention

The audit and its report

audit reads the source and checks it against every rule that has a static check. With --url it also runs Lighthouse and axe-core in your own Chrome, after asking, and maps their results to the same rule ids. Rules a machine cannot judge are listed as a checklist.

In the source

Missing alt, lang, title or viewport; zoom blocked; positive tabindex; click handlers on static elements; unlabelled fields; invalid autocomplete; focus outline removed; images without size; render-blocking scripts; fonts without font-display; oversized images; index keys; 100vh.

In a rendered page

Colour contrast, accessible names computed through components, landmarks and headings of the final page, focus order, target size, Lighthouse performance, SEO and best-practice audits.

By a person

Whether alt text means the right thing, the quality of error messages, reading order, keyboard traps in custom widgets, screen reader announcements, cognitive load.

Condensed output for agents

With --json the audit prints one line per rule, with the fix and every location as file:line and no other prose, so an agent spends tokens on findings. This is the real output for the react-vite example project:

Exit codes: 0 when nothing is at or above --fail-on (default serious), 1 when something is, 2 for a usage error, 3 when a requested tool is not available.

Ignoring a finding

Write fs-ignore <rule id> in a comment on the line or the line above, or list rule ids and paths under audit.ignore and audit.exclude in the profile.

Safe by default

Nothing you wrote is overwritten. Every file and block the command writes is recorded in .frontend-skills/install.json with its hash; uninstall removes a file only while its hash still matches and keeps a file you changed. --dry-run shows the plan and writes nothing.
